# Invoice Validation module — integration guide

This is a **separate Python/SQLite module** that sits alongside the existing
Node.js scripts in `fabricated-receipt-main`. It doesn't touch or replace
anything already there — the existing repo's `scripts/*.mjs` pull and grade
NYC Open Data for the join-faithfulness project; this module is the
downstream invoice-checking demo (Table 1 + Table 2 + a new Table 3), built
in Python because Streamlit needs it and SQL upserts are simplest against a
real database rather than flat JSON.

## Where each piece goes in your existing repo

```
fabricated-receipt-main/
├── scripts/               <- existing, untouched (Node .mjs, pull/failures/grain)
├── docs/                  <- existing, untouched
├── eval/                  <- existing, untouched
├── data/                  <- EXISTING folder, already gitignored.
│   ├── budget_and_schedule.json      <- existing, from scripts/pull.mjs
│   ├── spend_history.json            <- existing, from scripts/pull.mjs
│   ├── raw/                          <- NEW subfolder: put the two source CSVs here
│   │     ├── table1.csv              (Citywide Budget and Schedule export)
│   │     └── table2.csv              (Budget Spend History and Variance export)
│   └── capital_projects.db           <- NEW: SQLite db, generated by etl/upsert.py
│
├── db/                     <- NEW top-level folder
│   └── schema.sql          Table 1 / Table 2 / Table 3 / vendor tables
│
├── etl/                    <- NEW top-level folder
│   ├── upsert.py           CSV -> SQLite for Table 1 and Table 2
│   └── seed_table3.py      generates vendor_master, fms_vendor, 15 invoices
│
├── checks/                 <- NEW top-level folder (Python package)
│   ├── __init__.py
│   ├── db.py
│   ├── job_status.py       Check 1
│   ├── vendor_resolution.py Check 2
│   ├── duplicate_payment.py Check 3
│   └── run_checks.py       orchestrates all three for one invoice / all invoices
│
├── app/                    <- NEW top-level folder
│   └── streamlit_app.py    the frontend
│
└── requirements.txt         <- NEW, Python deps (streamlit, pandas, rapidfuzz)
```

Everything under `data/` stays gitignored, same as today — the `.db` file and
`data/raw/*.csv` should never be committed, consistent with the existing
`.gitignore` pattern for `data/`.

## Why SQLite, not the existing JSON files

`scripts/pull.mjs` writes flat JSON arrays, which is right for the
grain/faithfulness project (it re-derives everything with `Array.reduce` on
demand). This module needs indexed lookups by `fms_id`, a real primary key
on Table 3 to make upserts idempotent, and joinable vendor tables — a real
database is the right tool here, and SQLite keeps it dependency-free and
file-based like the rest of the repo (one `.db` file, no server to run).

## Run order

```bash
# from the repo root, after adding the new folders above
pip install -r requirements.txt

# 1. Load Table 1 and Table 2 from your CSV exports
python etl/upsert.py \
  --db data/capital_projects.db \
  --table1 data/raw/table1.csv \
  --table2 data/raw/table2.csv

# 2. Seed Table 3 + vendor tables, grounded in real fms_ids from step 1
python etl/seed_table3.py --db data/capital_projects.db

# 3. Launch the frontend
streamlit run app/streamlit_app.py
```

`etl/upsert.py` is safe to re-run any time you get a fresher CSV export —
it's keyed on `(fms_id, reporting_period)` / `(fms_id, year_month_reported)`
via `INSERT ... ON CONFLICT DO UPDATE`, so it refreshes existing rows and
adds new ones without ever duplicating.

## If you'd rather pull live instead of from CSV

`scripts/pull.mjs` already fetches `fb86-vt7u` and `qj5n-h5qp` as JSON. If
you want one source of truth, you could add a `--json` mode to
`etl/upsert.py` that reads `data/budget_and_schedule.json` /
`data/spend_history.json` directly instead of CSV — same upsert logic,
different reader. Say the word if you want that variant instead of/in
addition to the CSV path.
